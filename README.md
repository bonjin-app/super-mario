# PIPO JUMP 🤖

오리지널 캐릭터 플랫폼 액션 게임 (HTML5 Canvas, 60fps)
모든 캐릭터·스프라이트·사운드가 원작 없이 직접 디자인/구현했습니다.

## 실행

```bash
open index.html
# 또는
npx serve .   # → http://localhost:3000
```

## 조작법

| 키 | 기능 |
|---|---|
| ← → / A D | 이동 |
| Space / ↑ / W / X | 점프 (길게 누르면 높이) |
| **Z / Shift** | **달리기** (누른 채 이동) |
| **F / K** | **불꽃 발사** (꽃 획득 후, 최대 2발) |
| Enter | 시작 / 확인 |
| P / Esc | 일시정지 — **전체 조작표가 표시됨** |
| **↓ / S** | **파이프 진입** (진입 가능한 파이프 위에서) |
| **Q** | **타이틀로 나가기** (일시정지 중에만 — 오조작 방지) |
| **R** | **키 재설정** (일시정지 중에만 — 6개 조작을 차례로 지정, Enter 건너뛰기 / Esc 취소) |
| M | 사운드 on/off |
| B | BGM on/off |

조작 안내는 세 곳에서 확인할 수 있습니다.

1. **페이지 상·하단 바** — 웹 페이지의 DOM 크롬. 키 칩과 파워업 설명. 화면이 낮아지면 자동으로 접힘
2. **일시정지 화면** — `P` 를 누르면 전체 조작표
3. **상황별 힌트** — 코스 시작 시 `HOLD Z TO RUN`, 꽃 획득 시 `PRESS F TO SHOOT`,
   가시 적이 처음 화면에 들어올 때 `SPIKES! JUMP OVER - NEVER STOMP`, 체크포인트 통과 시 `CHECKPOINT!`,
   시간이 0이 될 때 `TIME UP!` — 각각 한 번씩만 표시

터치 기기에서는 하단 D-패드(◀ ▶)와 A(점프)·B(달리기)·F(발사) 버튼이 자동 표시되며,
키보드 안내 바는 숨고 안내 문구가 터치 표현으로 바뀝니다.

## 선택 가능한 히어로 (타이틀 화면에서 ←→)

| 히어로 | 캐릭터 | 속도 | 점프(소형/대형) |
|---|---|---|---|
| **PIP** | 모자 쓴 남자아이 | 2.7px/f | 82 / 90px |
| **MOCHI** | 사이드 포니테일 여자아이 | 3.02px/f | 76 / 83px |
| **BOLT** | 고양이 귀 후드 아이 | 2.54px/f | 91 / 99px |

히어로·몬스터·아이템 모두 도트를 찍지 않고 **곡선(타원·캡슐)으로 그려서 4배 슈퍼샘플 캔버스에 구운 뒤 안티에일리어싱으로 블릿**합니다.
지형만 픽셀아트로 남기고, 포즈는 팔·다리 오프셋 값이라 프레임별 아트가 없습니다.

레벨이 요구하는 최대 등반 높이는 4칸 파이프의 64px이며, 세 히어로 모두 소형 상태로 여유를 두고 넘습니다.

## 전체 플로우

```
로드 → 타이틀(히어로 선택, TOP) → READY 카드 → 코스
   ↓ 깃대 → 성으로 걸어감 → 팡파레 → 타임 보너스 정산
   ↓ x-1 → x-2 → x-3 → [WORLD n COMPLETE] → (n+1)-1 …
   ↓ 사망 → 목숨 카드(체크포인트 시 FROM CHECKPOINT) → 코스 재개
   ↓ 목숨 소진 → GAME OVER → [CONTINUE(해당 월드부터) / END(타이틀)]
   일시정지 → 전체 조작표 → 재개 또는 Q로 타이틀
```

플로우를 처음부터 끝까지 훑어서 막혀 있던 지점 4개를 채웠습니다.

- **TIME UP 이 무음이었음** — 시간이 0이 되면 아무 설명 없이 히어로가 그냥 죽어서, 밟혀 죽은 것과 화면이
  똑같았습니다. 전용 하강 2음 + `TIME UP!` 배너 + 사망 카드에 붉은 `TIME UP!` 표기
  (카드가 뜨기 직전 `startLevel()` 이 플래그를 지우기 때문에 리빌드를 건너 전달하고, 카드가 끝날 때 해제)
- **GAME OVER 가 막다른 길이었음** — 키 하나로 타이틀로 돌아가고 도달한 월드는 사라졌습니다. 이제
  `REACHED WORLD x-y` 와 함께 **CONTINUE(그 월드 1코스부터, 목숨 3) / END(타이틀)** 를 선택합니다.
  CONTINUE 시 점수는 0으로 초기화 — 하이스코어는 이미 적립되어 있으므로 이어하기로 부풀릴 수 없습니다
- **일시정지 중 나갈 방법이 없었음** — 코스를 벗어나려면 3번 죽어야 했습니다. `Q` 는 **일시정지 상태에서만**
  받아서 오조작으로 코스를 잃지 않고, 일시정지 화면에 안내가 적혀 있습니다
- **월드를 넘기는 순간이 밋밋했음** — x-3 클리어가 다른 코스와 똑같이 보이고 다음 카드가 `WORLD n+1` 이라고
  적힐 뿐이었습니다. 이제 x-3 도착에는 더 긴 플로리시가 울리고 클리어 패널에
  `WORLD n COMPLETE` / `NEXT: WORLD n+1-1` 이 추가되며, 패널이 260프레임(일반 코스는 120) 유지됩니다
- **하이스코어 적립 시점 추가** — 게임오버뿐 아니라 **코스 클리어마다, 그리고 Q로 나갈 때도** 저장.
  탭을 닫아서 끝난 런이 아무것도 남기지 않던 문제

## 보너스 룸 3종 — 한 방을 세 번 쓰던 문제

파이프 4개가 전부 같은 방으로 이어졌습니다. 코인 갤러리 2개, 벽돌 선반, `?` 블록, 18열의 출구.
분기 스위치가 있었지만 코인 한 줄을 한 칸 밀어주는 정도였고, 그건 두 번째 방이 아니라 같은 방입니다.
게다가 분기 기준이 `entry.tx % 3` — 파이프를 어디에 놓았느냐에 따라 우연히 결정되는 값이라,
4개 입구 중 2개가 같은 케이스에 겹치고 방 하나는 **코드에만 존재하고 게임에는 한 번도 나오지 않았습니다.**

입구가 자기 방을 지정하게 하고, 방 3개를 **동작이 다른 형태**로 다시 만들었습니다.

| 방 | 크기 | 동작 |
|---|---|---|
| **VAULT** | 22×15 | 걷고 뛰어서 모은다. 높은 코인 줄은 바닥에서 닿지 않아(점프 75px vs 높이 128px) 선반이 길이 된다 |
| **CHIMNEY** | 14×15 | **올라간다.** 계단식 석재 3단, 출구는 정상. 코인이 단마다 있어 마지막이 아니라 매 단에서 보상 |
| **TUNNEL** | 26×15 | **기어간다.** 2타일 높이 굴. 대형은 32px 구멍을 2px 여유로 통과하고 안에서는 점프가 안 된다 |

기하는 전부 두 숫자에서 나옵니다 — 대형 히어로 **30px**, 점프 **75px**. 그래서 보상 블록은 발판 위
**4행**에 놓습니다(3행이면 여유가 2px라 대형은 점프를 시작조차 못 합니다). 코인은 4~5행 위 = 서서가
아니라 비행 중에 먹는 위치. 방마다 적힌 숫자는 모두 이 두 케이스 중 하나입니다.

만들며 잡은 것 3가지, 전부 봇이 찾았습니다.

- **CHIMNEY 초안은 대형만 나갈 수 있었습니다.** 떠 있는 선반 2개를 걸었더니 소형(16px)이
  16px 틈으로 **선반 아래를 그냥 지나가** 수직굴 밑에 갇히고, 대형은 막혀서 올라갔습니다.
  타이머는 계속 갑니다. → 모든 단을 **바닥까지 solid**하게 바꿔서 지나갈 아래턱을 없앴습니다
- **TUNNEL에서 대형이 방에 갇혔습니다.** `?` 블록을 출구 파이프 옆 칸 4행 위에 뒀는데,
  머리 여유 18px로는 32px 파이프 입을 못 넘습니다. → 출구 접근 칸은 머리 위를 비웁니다
- **출구 입 위 2행은 무조건 비웁니다** — 기억하는 것보다 강제하는 게 쌉니다(첫 버전이 여기서 깨졌음)

## 수중 변주 패스가 물을 몰랐습니다 — 대형만 못 지나가는 바늘구멍

월드별 변주 패스의 모든 규칙은 **마른 땅을 걷는 히어로**를 전제로 씁니다. 발판 아래에 땅이 있는가,
파이프가 사거리에 있는가, 구덩이 위 공중이 비었는가. 땅에서는 그게 전부입니다 — 5행 위에는 하늘밖에
없으니까요. 그런데 라군에는 **천장과 거기 매달린 종유석**이 있고, 패스는 위를 보지 않습니다.

`always-big` 봇이 잡았습니다: **월드 3-3 88열에서 세 캐릭터 전부 정지.** 88~89열에 변주가 추가한
종유석(0~5행), 92열에 원래 있던 산호(8~12행) — 사이를 통과하는 물은 **6~7행 두 줄뿐**이었습니다.
30px 히어로에게 32px. 소형은 통과했고 대형은 못 했습니다. **플레이어가 강해질 때 나타나는 버그**,
레벨 결함으로는 가장 나쁜 형태입니다.

세 가지를 고쳤습니다.

- **물은 자기 어휘로 변주합니다** — 물고기·산호·종유석·코인 트레일. 걷는 적, 호퍼, 대포, 리프트,
  물 한가운데 벽돌 선반은 라군에 있을 이유가 없습니다 (검증: 물속에 물고기·글라이더 외 0마리)
- **성장물은 양옆 8열이 비어야 놓입니다** — 손으로 배치한 쌍은 12~14열 간격이고 그 리듬이
  위아래로 헤엄치게 만드는 것이므로, 변주가 그 사이를 파고들지 못하게 합니다
- **통행 불변식**: 3행 높이 상자로 스폰에서 홍수 채우기(flood fill)를 돌려 해안까지 닿지 않으면
  종유석 **끝**을 깎습니다(천장은 아래에서, 산호는 위에서 — 반대로 깎으면 물속에 기둥이 뜹니다).
  구덩이·가시 규칙과 같은 형태 — 저작은 틀려도 되고, 빌드가 결과를 내보내지 않습니다

측정: 12월드 수중 코스 6개 전부 **최소 통로 5행(80px)**, 3행 미만 없음.

## 라군 천장 아래로 하늘과 구름이 비쳤습니다

체크포인트가 수중 코스에서도 제대로 동작하는지 확인하려고 스크린샷을 찍어봤는데, 배경이 완전히
잘못돼 있었습니다 — 물속인데 하늘 그라디언트와 구름·먼 산·덤불이 그대로 스크롤되고 있었습니다.

타일 레이어는 이미 맞았습니다: 라군을 만들 때 "천장이 있어야 물이 하늘이 아니라 갇힌 공간으로
읽힌다"고 명시적으로 주석까지 남기고 0~1행에 천장 타일을 깔았습니다. 그런데 **배경 데코 레이어는
그 기억을 못 물려받았습니다** — `drawBackground()`가 산·언덕·구름·덤불을 매 코스마다 무조건 그리는데,
요새(`L.fortress`)만 벽 배경으로 따로 처리돼 있고 물(`L.water`)에는 그런 예외가 없었습니다. 결과: 돌
천장 바로 아래에서 파란 하늘과 뜬구름이 훤히 보이는, 코드 자체의 설계 의도와 정반대인 장면.

패럴랙스 데코는 카메라 위치에 따라 화면 속도가 다르게 스크롤되도록 저장된 x가 "그 데코가 화면에
보이는 카메라 구간"을 나타내는 방식이라, 개별 데코 하나하나를 "이건 물 위인가 해안인가"로 나누는 건
느린 레이어(마운틴 0.2배속 등)에서는 맞지 않습니다 — 한 데코가 카메라의 넓은 구간에 걸쳐 보이기
때문입니다. 대신 **지금 화면에 보이는 카메라 범위 자체**가 아직 완전히 물속인지를 검사해서, 그동안은
데코 루프를 통째로 건너뛰고, 화면 오른쪽 끝이 해안(`waterTo`)을 지나는 순간부터 정상적으로 그립니다.

측정: 잠수 구간에서는 데코 0장, 해안 근처에서 정상 복귀 확인. 코스 전환 지점 스크린샷으로 시각 확인.
회귀: 통과 주행 12월드×4코스×3히어로 144회(매 스텝 `draw()` 포함) 전부 유지.

## 점수에 갈 곳을 만들었습니다 — 랭킹 5줄과 무한 콤보의 끝

점수 규칙 자체는 이미 원작에 가까웠습니다 — 코인 200점, 밟기 콤보 사다리, 깃대 높이 보너스, 남은 시간
1초당 50점. 빠진 건 그 숫자를 **둘러싼 모든 것**이었습니다. 한 판의 결과가 `pipoHigh`라는 정수 하나에
적히고 두 화면에 "TOP 012345"로만 보였습니다 — 그 판이 실제로 어땠는지 남는 기록이 없고, 예전 판을
넘어서도 확인할 길이 없고, 이야기 없는 숫자 하나를 쫓을 이유도 없었습니다.

네 가지를 바꿨습니다.

- **판을 숫자가 아니라 사건으로 기록합니다** — 코인, 처치한 적, 최고 콤보. `GAME.run`이 게임오버까지
  누적되고, 게임오버 카드가 "164 COINS 71 FOES BEST CHAIN 6" 한 줄로 보여줍니다
- **TOP FIVE 랭킹표** — 점수·도달 월드·사용한 히어로를 `localStorage`에 저장합니다. 다섯 줄이 사다리가
  되는 지점입니다: 한 줄은 벽이고, 열 줄은 끝이 안 보이는 벽입니다
- **게임오버 카드가 이 판이 어디 들어갔는지 보여줍니다** — 랭킹에 들면 그 줄이 강조되고, 1위를 갈아
  치우면 NEW RECORD가 깜빡입니다
- **밟기 콤보가 8연쇄에서 8000점을 반복하는 대신 1UP으로 끝납니다** — 8연쇄를 땅에 안 닿고 해낸 건
  의도한 플레이고, 원작이 그걸 보상하는 화폐는 목숨뿐입니다

코드로 만질 수 있는 부분(적 처치 집계, 코인 집계, 콤보 사다리)은 전부 **한 곳**에서 셉니다 —
`addScore`에 `type`이 있는 대상만 적으로 세는 식으로, 나중에 적이 추가되면 그날부터 자동으로
집계에 들어갑니다. 열두 곳에 흩어진 호출부를 전부 기억해야 하는 방식이 아닙니다.

측정: 실제 죽음 경로(코인 획득 → 콤보 → 목숨 소진 → gameover 전환)를 그대로 태워 랭킹에 오르는지,
낮은 점수가 표를 덮어쓰지 않는지, 0점이 실제 기록을 밀어내지 않는지, 저장이 깨졌을 때 화면 전체가
아니라 그 줄만 잃는지 확인했습니다. 320px 논리 화면 기준 극단값(999999점, W99-4, MOCHI, 코인 999,
적 999)에서도 어떤 줄도 화면을 넘지 않았습니다.

바로 다음 검증에서 그 1UP 자체가 **무한 목숨 익스플로잇**이었다는 걸 잡았습니다. 첫 버전은 증가시킨
**뒤의** 콤보값(`GAME.combo`)으로 "사다리 끝에 닿았는가"를 판정했는데, 그 값은 체인이 끊기기 전까지
계속 사다리 끝(9)에 머뭅니다 — 즉 9번째 스톰프 이후로 **끊지 않는 한 스톰프마다** 목숨이 하나씩
늘어납니다. 셸을 걷어차고 일렬로 선 적을 타고 내려가는 흔한 플레이만으로도 15연쇄에 목숨 7개를 얻는
걸 재현했습니다. 판정을 증가시키기 **전의** 콤보값으로 바꿔, 사다리를 처음으로 넘는 그 스톰프 한 번에만
지급하도록 고쳤습니다 — 15연쇄·60연쇄 모두 정확히 목숨 1개, 체인을 끊고 다시 9까지 채우면 별개로 1개 더.

그 다음엔 표 자체의 빈틈을 하나 더 찾았습니다: `pipoHigh`(코너에 보이는 숫자)는 코스 경계·Q로 나가기·
게임오버 세 곳에서 갱신되는데, TOP FIVE 표는 **게임오버(죽음)에서만** 적립됐습니다. 좋은 판을 하다가
Q로 스스로 나가면 코너의 숫자는 갱신되지만 그 판은 랭킹표에 **영원히** 들어가지 않고, 다음에 그보다
낮은 점수로 죽으면 코너 숫자와 표 1위가 서로 다른 판을 가리키는 상태가 됩니다. 판이 끝나는 두 경로
(죽음, Q로 나가기) 중 하나만 기록하고 있던 것 — Q 경로에도 `submitScore()`를 추가해 죽음과 동일하게
반영되도록 했습니다. 보여줄 카드가 없을 뿐, 기록은 남습니다.

이어서 사운드 커버리지를 훑었습니다 — 25개 큐(기존 22개 + 이번에 추가한 것)가 전부 실제로 호출되고
있는지, 뮤트 시 오실레이터가 0개 생성되는지 전부 확인. 코드 자체는 빠짐없이 연결돼 있었지만 빈틈 하나가
있었습니다: 게임오버 카드가 랭킹 1위를 초록색으로 강조하고 "NEW RECORD"를 깜빡이는데, 소리는 기존
하강조 `gameOver()` 5음뿐이라 그 성취를 알리는 오디오가 없었습니다. 짧은 상승 3음 차임(`record()`)을
추가하고, `gameOver()`의 하강이 끝나는 시점(1초 뒤)에 걸리도록 지연을 줬습니다 — 두 모티프가 서로
싸우지 않게. 목숨이 걸린 `oneUp()`의 6음 런이나 코스 클리어의 `fanfare()`(8음, 더 큰 순간)와는 겹치지
않는 별개의 소리입니다. 순위 2~5위는(카드에 NEW RECORD 텍스트가 없는 자리) 이 차임을 울리지 않고,
Q로 나가는 경로는 원래부터 일시정지·나가기가 조용한 전환이라는 기존 관례를 그대로 따라 소리를 넣지
않았습니다.

그 다음 월드별 밀도(적·가시·코인·산호)를 월드 1~12로 측정해 보니, 수중 코스의 **산호/종유석이 lap이
올라가도 98개에 완전히 고정**돼 있었습니다. 물고기 수는 정상적으로 늘고(11→17) 있었는데 산호만
멈춘 것 — 원인은 지난 라운드에 needle 버그를 막으려고 넣은 `clearAround(x, 8)`(양옆 18칸 완전 개방
요구)였습니다. 저작된 산호 쌍은 12~14칸 간격으로 서 있어서 18칸 개방 구간이 라군 전체에 **한 번도**
생기지 않았고, 그래서 성장 루프가 매 라운드 실행은 되지만 아무것도 놓지 못하는 죽은 코드였습니다.
"안전하게 고쳤다"고 검증까지 했던 코드가 실은 기능을 죽여놓은 채였던 셈입니다.

이 needle 버그는 그 뒤에 넣은 **통행 불변식**(홍수 채우기 + 종유석 끝 트리밍)이 이미 막고 있으므로,
배치 시점 여유를 8칸에서 4칸으로 줄였습니다 — 조각 하나가 최대 4행이라 단독으로는 13행짜리 수로를
막을 수 없고, 그래도 겹쳐서 문제가 생기면 통행 불변식이 사후에 잡습니다. 측정: 산호가 98 → 112~118로
lap을 따라 늘어나고, 20월드 수중 코스 전부 최소 통로 5행 유지, 통과 주행 12월드 × 4코스 × 3히어로
소형·대형 각 144회 전부 클리어.

마지막으로 모바일 터치 반응성을 직접 확인했습니다. 멀티터치(다른 버튼 두 개를 동시에 누르는 대각선
이동+점프), 44px 타깃 크기, 버튼 간 겹침은 전부 정상이었지만 레이아웃 자체에서 두 가지를 찾았습니다.

- **세로 모드에서 A(점프) 버튼이 화면 밖으로 잘렸습니다.** `#pad`가 `space-between`인데 좌측 그룹
  (방향+파이프진입, 188px)과 우측 그룹(달리기+발사+점프, 216px)의 합이 패딩까지 428px — 375~390px인
  거의 모든 폰의 세로 화면보다 넓습니다. 파이프 진입용 `▼` 버튼을 나중에 좌측 그룹에 추가하면서 세로
  모드 폭을 다시 검증하지 않은 게 원인으로 보입니다. 가장 중요한 입력인 점프가 폭 375px 화면에서 절반
  가까이 잘려 있었습니다. 랜드스케이프에 이미 있던 "묶어서 줄바꿈" 트릭(달리기+발사 위, 점프 아래로
  146px)을 세로 모드의 양쪽 그룹에 똑같이 적용해 좌측 130px·우측 146px, 합계 300px로 줄였습니다 —
  360px 폭 화면에도 여유가 남습니다.
- 그 수정으로 패드가 2행이 되며 **파워업 안내 문구와 겹치는** 2차 문제가 생겼습니다. 하단 여백
  예약값이 예전 1행 패드 높이(112px) 기준이었던 것 — 새 2행 높이(146px 콘텐츠 + 14px 패딩 ≈ 160px)에
  맞춰 168px로 올렸습니다.
- 검증 중에 **랜드스케이프에서도 같은 종류의 문제**를 찾았습니다: `▼` 버튼이 추가되면서 좌측 그룹이
  188px가 됐는데, 플레이필드 옆 여유 공간은 191px뿐이라 9px가 캔버스 좌하단 모서리를 덮고 있었습니다.
  "812x375에서 겹침 없음 확인"이라는 기존 주석은 `▼` 버튼이 추가되기 전 검증이었던 것으로 보입니다.
  같은 줄바꿈 트릭을 좌측 그룹에도 적용해 130px로 줄여 해결.

측정: 375×812, 390×844, 360×640, 812×375(랜드스케이프, 강제 TOUCH) 전부 패드 오버플로 0·캔버스 겹침
0·파워업 문구 겹침 0·터치 타깃 44px 이상·버튼 간 겹침 0.

## 키 리매핑 — 마지막 접근성 구멍

배열이 `switch (e.key)` 에 하드코딩되어 있었습니다. QWERTY 키보드에 양손이 자유롭고 방해물이 없는
사람에게는 괜찮지만, 키보드·손·보조기기가 다른 사람은 손댈 수 없습니다. 바인딩을 **데이터로** 바꾸고
일시정지 화면에서 편집·저장합니다.

- **기본값은 그대로** — 각 액션이 기존 키 목록을 전부 유지하므로, 리바인드 화면을 한 번도 열지 않는
  플레이어에게는 아무것도 바뀌지 않습니다 (17개 기본 매핑 회귀 확인)
- **`Escape` 는 절대 재할당되지 않습니다** — 리바인드하는 메뉴에서 나가는 길을 리바인드로 잃는 상태는
  플레이어가 도달할 수 없어야 합니다
- **키를 빼앗지만 비우지는 않습니다** — 다른 액션이 쥔 키를 할당하면 그쪽에서 제거하되,
  그 액션의 **마지막 키라면 거부**합니다(이동 수단을 스스로 없앨 수 없음)
- **일시정지 화면의 조작표가 실제 바인딩을 읽습니다** — 기본값 복사본이 아니라 데이터에서 생성.
  페이지 상·하단 크롬의 키 칩도 같은 데이터로 다시 그립니다
- **저장은 기존 설정과 함께**, 손상된 값은 액션 단위로 기본값으로 폴백

만들며 잡은 것: 리바인드 핫키를 `K` 로 뒀는데 **`K` 는 발사의 기본 바인딩**이라 `normKey` 가 `fire` 를
돌려주고 핫키가 조용히 아무 일도 하지 않았습니다. **어떤 바인딩이든 가릴 수 있는 핫키는 핫키가 아니라서**,
키다운에서 원시 키(`R`)로 처리하도록 옮겼습니다 — 플레이어가 R 을 발사에 할당해도 계속 동작합니다.
조작표 레이블 `ENTER PIPE` 가 44px(7자) 컬럼을 넘어 값과 겹치던 것도 함께 고쳤습니다.

## 음악 깊이와 저감 모션 (접근성)

### 음악 — 2마디를 40번 듣던 문제

모든 트랙이 32스텝(2마디), 리드와 베이스만 있고 **타악기가 없었습니다.** 코스는 2~3분이니
같은 2마디를 40번 듣게 되고, 박자를 잡아 주는 것도 없었습니다.

- **트랙당 64스텝** — 기존 2마디를 A 섹션으로 두고 각 트랙에 대비되는 B 섹션을 붙였습니다
  (MEADOW은 5도 위로, SUNSET은 한 옥타브 아래, MIDNIGHT은 펄스를 2배로, CAVERN은 4도 위,
  FORTRESS는 올라가되 해결하지 않고, LAGOON은 3도 아래로 가라앉으며 타악기가 심박으로 얇아짐)
- **트랙당 퍼커션 라인** — 킥(저역 스윕)·햇(짧고 밝음)·스네어 3종. **music 버스에 실어서**
  기존 덕킹(팡파레·1UP·사망 시 음악 감쇠)이 드럼에도 그대로 적용됩니다
- 스케줄러가 루프 길이를 **트랙에서 읽습니다**(32 하드코딩 제거)

### 저감 모션 — `prefers-reduced-motion`

이 게임은 화면을 흔들고, 프롬프트를 초당 2회 점멸시키고, 스타 팔레트를 2프레임마다 순환하고,
피격 무적 중 히어로를 깜빡입니다. 시스템에 "모션을 줄여 달라"고 설정한 사람에게는 과합니다.

- **화면 흔들림: 끔** (장식입니다)
- **점멸 프롬프트: 고정** (어느 쪽이든 같은 말을 합니다)
- **스타 팔레트: 4배 느리게** — 다만 "곧 끝난다"는 가속은 유지합니다(정보를 나르는 점멸이라
  제거가 아니라 완화)
- **피격 무적 깜빡임: 유지** — 지금 맞지 않는다는 사실을 알려 주므로, 이걸 숨기면 표현이 아니라
  게임이 바뀝니다
- 미디어 쿼리를 **실시간 구독**합니다 — 탭을 열어 둔 채 설정을 바꿔도 다음 프레임부터 반영

## 수중 코스 (레이아웃 4: LAGOON) — 손이 하는 일이 바뀌는 추가

리프트 이후 동작 세트가 그대로였습니다: 달리기·점프·밟기·발사·탑승·진입. 수중은 **동사가 바뀝니다** —
점프 대신 **스트로크**를 하고 **밟을 수 없습니다**.

- **물리**: 중력 0.38→0.115, 종단 낙하 5.5→1.65px/f, 최대 속도 2.7→1.55, 스트로크 임펄스 -2.55
  - 스트로크는 **코요테 타임도, 지면도, 길게 누르기도 없습니다** — 누르고 있어도 더 높이 안 갑니다
    (측정: 탭 37.5px = 홀드 37.5px). 이게 수중을 "비행 레벨"로 만들지 않는 장치입니다
  - 물속에선 **저항**이 붙어 방향을 놓으면 미끄러지듯 멈춥니다
- **밟기 금지**: 스트로크에는 체중이 없고 원작도 허용하지 않습니다. 답은 불꽃과 스타
  - 물고기는 글라이더와 **모션을 공유**(사인 궤도)하지만 타입이 달라서, 밟기 규칙을 각각 따로 가집니다.
    처음엔 공용 분기에만 물 가드를 넣어서 **라군의 물고기만 밟을 수 있었습니다**
- **별도 빌더가 아니라 5번째 레이아웃**으로 저작했습니다 — 골 시퀀스·체크포인트·변주 패스·플로우가
  전부 그대로 동작합니다. 물은 172번 열에서 끝나고 마지막 20타일은 마른 땅이라 **물에서 걸어 나와**
  평소처럼 깃대로 마무리합니다. 물리 전환은 레벨 모드가 아니라 **위치 판정**(`inWater`)입니다
- 산호는 바닥과 천장에서 번갈아 자라고 **항상 4타일 이상의 수로**를 남깁니다(전 컬럼 실측)
- 시간 제한 400→500 (이동이 느려진 만큼)

만들며 잡은 것: **LAGOON 팔레트를 만들고 선택하지 않아서** 수중 코스가 평범한 석양 필드로 그려지고
있었습니다(캐번 팔레트와 같은 종류의 실수 — 이번엔 만든 직후에 스크린샷으로 잡았습니다).
그리고 통과 주행 하네스를 **수영 가능**하도록 확장했습니다: 물에서는 앞이 막히거나 바닥에 가까워지면 스트로크.

## 진행 저장, 그리고 4번째 레이아웃 (테라스)

제가 직접 지목한 약점 두 개를 처리했습니다.

### 진행 저장 — "껐다 켜면 1-1"

- 저장하는 것은 **도달한 최고 월드 하나**입니다. 점수·목숨은 저장하지 않습니다 —
  시작점을 여는 건 진행이지만, 점수를 세션 너머로 들고 오면 하이스코어가 의미를 잃습니다
- 타이틀에서 `↓` 로 해금된 월드를 순환 선택(해금이 1개뿐이면 그 줄을 아예 그리지 않음 —
  선택지 하나인 컨트롤은 잡음입니다). `startWorld` 를 조작해도 `maxWorld` 로 클램프
- 게임오버의 CONTINUE 는 여전히 **죽은 월드**에서 재개합니다(해금과 무관)

### 레이아웃 3: 테라스 — 월드 4면 모든 구조를 다 본 문제

기존 3레이아웃은 모두 같은 모양이었습니다: 평지 하나 + 파이프 + 5·9행 부유 블록 + 구덩이 3~4개.
새 레이아웃은 **지형 자체가 움직입니다** — 2단 테라스(11행)와 한 칸 더 높은 선반(10행),
그 위에 코인 열과 보상 블록. 구덩이는 둘뿐이고 대신 낙차가 있습니다(테라스에서 떨어져도 바닥에 착지).

- **레이아웃 로테이션도 월드마다 밀립니다** — 4레이아웃 × 필드 3코스: 월드1은 0/1/2,
  월드2는 1/2/3, 월드3은 2/3/0. 같은 세 개를 같은 순서로 두 번 만나지 않고,
  레이아웃×팔레트 조합이 매 랩 바뀝니다
- **지형 고도차를 위해 스포너를 일반화**했습니다. 모든 스포너가 13행을 하드코딩하고 있어서
  테라스 위에서는 자기 순찰병을 지형에 묻었을 것입니다. `surfaceRow(x)` 로 실제 표면에 앉힙니다
  - 처음엔 5행부터 스캔해서 **워커 409기가 공중의 벽돌 위로 올라갔습니다** — 지형 행(11~14)만
    보도록 좁혔습니다
  - 그 결과 **기존에 계단·대포 발판 안에 박혀 있던 워커 22기가 표면으로 올라왔습니다** —
    이전에는 지형에 파묻힌 채 스폰되고 있었던 것입니다
- **고지대 이륙의 구덩이 여유는 9타일이 아니라 14타일**입니다. 9행 블록(발 144)에서 뛴 아치는
  바닥 평면을 다시 지날 때까지 약 8타일을 가고, 테라스(발 176)에서는 7타일입니다.
  새 레이아웃의 두 구덩이가 정확히 그 거리에 있어서 선반에서 뛴 히어로가 매번 구멍 안으로
  떨어졌습니다 — 두 구덩이를 옮기고 변주 패스의 클러스터 규칙도 14타일로 넓혔습니다

## 타이틀 화면 — 죽어 있던 데이터와 읽히지 않던 하단

- **히어로 블러브가 처음부터 데이터에만 있었습니다** — `CHARS` 의 `blurb`(CAP BOY / TWIN TAIL / CAT HOOD)를
  프로젝트 내내 어디에도 그리지 않고 있었습니다. 선택된 히어로 카드에만 표시(3개를 한 번에 띄우면 잡음,
  하나면 캡션). 카드 높이를 64→68px 로 늘리고 이름·바·범례·시작 안내를 4~6px씩 재배치해
  **모든 행이 5px 이상 여유** 를 갖도록 실측 확인
- **하단 텍스트가 벽돌 무늬 위에 얹혀 있었습니다** — 푸터 스크림이 0.78 이라 벽돌 줄눈이 그대로 비쳐서
  TOP 점수가 텍스처에 묻혔습니다. 0.90 + 상단 금색 1px 룰 → 워시가 아니라 패널로 읽힙니다

골 시퀀스도 함께 점검했습니다. 계단이 벽돌처럼 보여서 "대형 히어로가 계단을 부술 수 있다"고 의심했지만,
코드는 `'X'`(지형 타일)이었고 팔레트를 잘못 읽은 것이었습니다 — 원작과 같은 구성이라 손대지 않았습니다.

## 보너스 룸이 두 라운드 동안 요새로 그려지고 있었습니다

퀄리티 점검 중 **실제 버그**를 찾았습니다. 두 상수가 모두 `THEMES.length - 1` 로 정의돼 있었고,
요새 팔레트를 캐번 뒤에 추가하면서 **둘이 같은 인덱스(4)** 가 됐습니다. 결과: 모든 보너스 룸이
캐번이 아니라 요새 팔레트와 요새 트랙으로 재생됐습니다 — 원작의 파란 지하를 만들어 놓고
두 라운드 동안 죽은 코드로 두고 있었던 셈입니다.

`THEMES.findIndex(t => t.name === 'CAVERN')` 로 **이름으로 조회**하게 고쳤습니다. 선언 순서에
의존하는 정체성은 다음 추가를 기다리는 버그입니다. (검증: 코스 SUNSET → 룸 CAVERN 팔레트·트랙 →
복귀 SUNSET)

**요새 클리어 헤드라인**도 분리했습니다. 깃대가 아니라 보스 밑에서 다리가 빠지는 결말인데
`COURSE CLEAR` 라고 적는 건 게임에서 유일하게 "이겼다"는 느낌을 줘야 할 순간을 깎아내립니다 →
**`FORTRESS FALLS`** (붉은 헤드라인).

그리고 1-1 의 밀도도 재봤습니다: **0~20타일 완전히 비어 있고, 첫 워커가 22번, 40번까지 4기.**
전체는 224타일에 49기(4.6타일당 1기)지만 2~5기 묶음과 빈 구간이 번갈아 나옵니다 — 원작의 페이싱과
같은 모양이라 손대지 않았습니다.

## 요새 2차 퀄리티 패스 — 비어 있던 회랑과 읽을 수 없던 죽음

요새에 **적이 하나도 없었습니다**(`enemies: []`). 용암·파이어바·보스뿐이고 그 사이는 10~14타일씩 비어 있었습니다.

- **BLAZE** — 용암에서 솟구쳐 떨어지는 불꽃. 밟을 수 없고 **불꽃으로도 죽지 않습니다**(자기가 불이니까).
  못을 "치우는" 대상이 아니라 "타이밍을 재는" 대상으로 만듭니다
- **순찰병** — 돌바닥 위의 쉘리. 회랑이 쉼터가 아니라 회랑이 되도록

그리고 그 과정에서 이 프로젝트가 계속 거부해 온 **읽을 수 없는 죽음**을 하나 더 만들어 놓고 잡았습니다.

- **점프를 결심한 순간 못은 비어 있었고, 공중에 있는 동안 불꽃이 솟았습니다.** 계측으로 원인을 특정
  (`hurtOrKill by blaze at x334.8 y132.4`, 이륙 시점 트레이스는 `blaze down`). 두 규칙으로 해결:
  1. **못 위에 이미 떠 있는 히어로에게는 발사하지 않습니다** — 파이프 플랜트가 "위에 서 있으면 안 나온다"로
     같은 문제를 이미 해결해 둔 전례가 이 코드베이스에 있습니다
  2. **모든 발사를 예고합니다** — 20프레임 동안 수면에서 거품이 오릅니다
- **공중 체류 비율 상한** — 첫 수치(랩 7에서 주기 94, 파워 8.7)는 못이 **62% 시간 막혀** 있었습니다.
  체공 시간이 `2*power/0.30` 이므로 주기 하한 132 + 파워 증가 완화로 **전 랩 33~41%** 로 고정
- **정지 상태로는 못을 건널 수 없었습니다** — 실측: 정지 점프 도달 **29~31px**, 상승 76~91px 인데
  2칸 못은 36px, 3칸 못은 52px 필요. 불꽃을 기다리라고 요구하면서 기다린 사람은 건널 수 없는 구조였습니다.
  못을 3~4칸으로 넓히고 **2타일 발판**을 중앙에 띄워 8/8·16/16px 두 번의 홉으로 나눴습니다
  (16px 발판을 먼저 시도했는데 걷는 속도의 점프가 **0.2px 차이로 지나쳤습니다** — 트레이스로 확인)
- **5행 블록이 순수한 함정이었습니다** — 9행 선반에 선 대형 히어로가 뛰면 48px 위의 5행 쌍에 머리를 찍고
  4타일 앞 못으로 떨어집니다(MOCHI 대형, 월드 3~5에서 재현). 요새의 5행은 닿지 않는 장식이므로 제거 —
  수직 재미는 필러와 파이어바가 담당합니다

## 요새 퀄리티 패스 — 빈 공간과 없는 피드백

만든 직후의 요새를 필름스트립으로 훑어보니 두 가지가 나왔습니다.

**요새가 검은 빈 공간이었습니다.** 1~4행, 6~8행, 10~12행이 코스 전체에서 순수한 검정 — 필드 코스는 그 자리를
하늘 그라디언트·구름·언덕이 채우는데, 요새는 `decos: []` 에 거의 검은 하늘이라 **매 프레임의 2/3가 아무것도
아니었습니다.** 성 내부에 실제로 있는 것을 넣었습니다:

- **타일링 벽면** — 지형과 같은 엇쌓기를 더 어둡게, 상단 하이라이트 없이. 위치 해시로 2종을 섞어
  128타일 벽이 벽지처럼 보이지 않게 합니다. 0.5 패럴랙스로 플레이필드 뒤에 있음을 알립니다
  - 첫 시도는 `-0.62` 로 어둡게 했는데 **텍스처가 있는데 보이지 않았습니다** — `-0.40` 으로 올려서
    "지형 뒤에 있을 만큼 어둡고 벽으로 읽힐 만큼 밝은" 지점을 잡았습니다
- **필러와 창** — 배경 전용, 충돌 없음. 필러는 천장에서 바닥까지 176px(96px 은 허공에서 끊겨 매달린 토막으로
  보였습니다), 좁고 어두웠던 첫 버전은 벽의 이음매처럼 읽혀서 폭 20px + 밝은 좌면·어두운 우면·양단 주두로 다시 그렸습니다.
  창은 알파 0.55 로는 안 보여서 0.92 로 올렸습니다
- 배치는 파이어바·다리에서 떨어뜨립니다 — 플레이어가 읽고 있는 위험 뒤에 장식이 겹치면 안 됩니다

**보스에게 불꽃을 쏘면 아무 일도 없었습니다.** 보스는 적 목록에 없어서 화염구가 그대로 통과했고,
플레이어에게는 "이 방법이 아니다"가 아니라 **버그로 읽혔습니다**. 이제 흡수하며 번쩍이고 금속음이 납니다 —
답은 여전히 다리지만, 질문에는 답이 돌아옵니다. 그리고 보스가 처음 화면에 들어올 때 **1회 포효 + `REACH THE
AXE BEYOND IT`** — 밟을 수도 태울 수도 없는 적은 원하는 걸 한 번은 말해 줘야 합니다.

## 적 2종 추가 — 공중과 원거리

로스터가 5종이었고 그중 4종이 걷습니다. **공중을 차지하는 적도, 화면 밖에서 위협하는 적도 없었습니다.**
모든 조우의 답이 "밟거나 넘거나" 하나였습니다.

- **GLIDER** — 공중 사인 궤도(진폭 16~24px), 중력 없음. 밟을 수 있지만 **높이가 계속 바뀌므로**
  점프를 겨누는 동안 표적이 움직입니다. 14px 크기에서 "공중"으로 읽히게 하는 건 프레임마다 젖는 날개입니다 —
  몸통만 그렸을 때는 떠 있는 워커처럼 보였습니다
- **CANNON + BOLT** — 자체 발판(U 블록) 위에 선 고정 포대. **포신 자체는 무해**하고 BOLT 를 발사합니다.
  BOLT 는 중력 없이 수평 직진하며 밟을 수 있고 접촉하면 피해입니다 — 위치가 아니라 **타이밍**의 위협:
  준비됐든 아니든 날아옵니다
  - 지나간 플레이어의 등에는 쏘지 않습니다. 그건 위협이 아니라 잡음입니다
  - BOLT 는 카메라를 벗어나면 회수됩니다
- **공중 적은 지상 배치 패스에서 면제**됩니다(`air` 플래그) — 글라이더를 땅에 내려놓거나 대포를
  다른 워커 칸으로 밀어내면 안 되니까요. 체크포인트 탐색의 "3타일 내 적 없음" 조건도 공중 적은 세지 않습니다

만들며 잡은 것: **대포 발판이 구덩이 도움닫기를 막았습니다**(2타일 벽). 감사 규칙을 먼저 넣었더니
BOLT/월드5-1 이 87번 열 구덩이에 빠지는 실패로 정확히 잡혔고, 저작 위치 1곳(126→112)과
변주 조건(클러스터와 같은 9타일 여유)을 고쳤습니다. `noPitNear` 를 선언 전에 쓰는 TDZ 도 함께 나왔습니다.

## 요새 코스와 보스 (x-4) — 월드의 클라이맥스

게임에 **클라이맥스가 없었습니다.** 월드가 그냥 다음 월드로 굴러갔습니다. 이제 각 월드는 **요새(x-4)**로 끝납니다.

- **FORTRESS 팔레트와 전용 트랙** — 돌·용암·검은 하늘. 베이스에 단2도를 깔고 리드는 해결되지 않습니다.
  "여기 있으면 안 된다"는 소리
- **128타일**(필드 코스는 198) 3구성: 용암 건너기 → 파이어바 회랑 → 다리
- **용암** — 구덩이와 같은 규칙: **스타 무적도 무시하고 즉사**합니다. 무적이 무효화하는 위험은 위험이 아닙니다.
  모든 용암 못 위에는 블록 다리가 있어 건너기가 점프 문제가 되고, 실패해도 닿을 수 없는 구덩이가 아니라 용암입니다
- **파이어바** — 블록을 축으로 도는 4~5링 사슬. 링의 중심만 판정하므로 보이는 것과 맞는 판정이고,
  시드 각도 + 고정 회전율이라 부활 후에도 같은 위치입니다. 용암 위에는 놓지 않습니다 —
  물러설 수 없는 위험은 이 게임이 계속 안 넣기로 결정해 온 종류입니다
- **보스** — 다리를 왕복하며 불을 뱉고, 주기적으로 도약합니다. **밟을 수 없고**(가시 워커와 같은 처벌),
  불꽃으로도 죽지 않습니다. 답은 다리입니다
- **도끼** — 다리 건너편. 닿으면 다리가 far end 부터 3프레임마다 한 칸씩 무너지고, 보스가 함께 떨어지고,
  월드가 완료됩니다(+5000점). 원작이 도끼를 답으로 만든 이유가 있습니다 — 체력 게이지 없이 읽히는 결말
- **보스의 불꽃은 히어로의 불꽃과 같은 투사체**입니다. `foe` 플래그 하나로 갈라지며,
  이게 없을 때는 보스가 자기 부하를 죽이고 플레이어는 건드리지 못했습니다
- 월드 완료 시점이 x-3 에서 **x-4 요새 함락**으로 이동했습니다

만들며 잡은 것: 다리 붕괴 인덱스가 하나 밀려 **마지막 판자가 항상 남았습니다**(붕괴 후에도 건널 수 있었음).
그리고 보스 아트가 히어로용 `blob`/`OUTLINE` 을 참조해 **스프라이트 빌드 시점 TDZ 로 스크립트 전체가 죽었습니다** —
적 전용 `foeBlob`/`FOE_OUTLINE` 로 교체.

## 월드별 변주 (8월드 = 3레이아웃 반복 문제)

가장 큰 구조적 약점이었습니다: **월드 5는 월드 1에 적이 빨라진 것**뿐이었습니다. 3개 레이아웃이 계속 돌았습니다.

- **테마 로테이션에 월드 오프셋** — 월드1 MEADOW/SUNSET/MIDNIGHT, 월드2는 SUNSET 부터, 월드3은 MIDNIGHT 부터.
  3레이아웃 × 3팔레트가 되어 연속한 두 월드가 같은 팔레트로 열리지 않습니다
- **시드 변주 패스** — `(world, lv)` 로 결정론적. 같은 코스는 방문할 때마다 동일하고, 한 랩 전과는 다릅니다.
  적(46→58/코스), 가시(3→6), 벽돌·코인 클러스터, 랩 3부터 리프트 1기 추가
- **모든 추가물은 기존 교정 패스의 검사를 받습니다** — 변주를 구조 패스보다 **먼저** 돌리므로,
  손으로 저작한 콘텐츠와 똑같은 규칙(구덩이 위 금지, 가시 상공 확보, 한 칸 한 마리, 보상 재배치)이 적용됩니다

변주를 만들며 드러난 것들:

- **패스 순서가 틀려서 26곳이 규칙을 위반**했습니다 — 변주가 교정 패스보다 늦게 돌아 검사를 받지 않았습니다.
  순서를 바꾸고 `airClear` 헬퍼를 위로 끌어올렸습니다
- **9행 클러스터가 파이프 등반과 구덩이 도움닫기를 덮어 3개 월드가 통과 불가**가 됐습니다.
  9행(y=144)은 모든 점프 궤적 안이라 엄격한 검사(도움닫기 지반·파이프 유무·아래 비어 있음)를,
  5행(y=80)은 지상 점프 정점(머리 y=117)보다 위라 겹침만 검사합니다
- 그런데 5행도 **고지대에서 뛰면 닿습니다**. 블록 위에서 뛴 정점이 5행을 찍어 구덩이에 빠졌습니다 —
  구덩이 배제 폭을 **측정값 기준 9타일**(달리기 점프 6타일 + 이륙 여유, BOLT 91px 점프는 머리가 y=101)로 확정
- **추가 리프트가 구덩이 위에 놓이면 함정**입니다. 위에서만 단단하니 달려서 건너던 플레이어가 데크에 착지하고
  반대쪽으로 걸어 나가 떨어집니다 (월드 14-3에서 발견)
- **체크포인트가 두 코스에서 사라졌습니다** — 적이 늘어 "3타일 내 적 없음" 조건을 만족하는 칸이 없었습니다.
  탐색 폭을 70으로 넓히고, 그래도 없으면 **가까운 적을 회수**합니다. 체크포인트가 워커 한 마리보다 가치 있습니다
- **가시를 놓을 자리가 없으면 평범한 워커로 강등**합니다(36코스에 1회 발생). 밟을 수 있는 적이
  천장 밑 가시보다 낫습니다

## 파이프 보너스 룸 (두 번째 지역 타입)

지금까지 게임은 **한 종류의 공간**만 있었습니다. 진입 가능한 파이프에 `↓` 를 누르면 지하 코인방으로 내려갑니다.

- **CAVERN 팔레트와 전용 트랙** — 원작의 파란 지하 톤. 보너스 룸의 요점은 *지상과 전혀 다르게 보이는 것*이라
  테마·음악을 모두 갈아탑니다. 트랙은 두 마디, tempo 0.14 — 15초 있다 나오는 곳이니 숨을 참는 느낌
  - 코스 테마 로테이션은 `(lv-1) % 3` 이라 4번째 팔레트를 추가해도 안전하지만, `% THEMES.length` 로 적혀 있어서
    **우연히** 맞고 있었습니다. `COURSE_THEMES = 3` 상수로 명시했습니다
- **진입 가능한 파이프는 스스로 말합니다** — 나머지 모든 파이프는 닫혀 있고, 이것만 입구가 뚫려 있습니다.
  좌/우 타일을 따로 구워 **하나의 입구로 이어지게** 했습니다(두 개의 사각형은 텍스처처럼 보였습니다).
  처음 그 위에 서면 1회 힌트
- **진입은 컷이 아니라 하강** — 14프레임 동안 가라앉고, 그 위에 파이프 입구 타일을 다시 그려 **파이프 뒤로**
  들어갑니다. 검은 화면에서 스왑, 기존 코스 페이드로 새 장소가 올라옵니다. 나올 때는 역순으로 파이프에서 솟습니다
- **출구는 다른 파이프** — 코스가 지정한 앞쪽 파이프로 나오므로 우회로가 진행도 사 줍니다
  - 처음 손으로 적은 출구 컬럼 3개(60·68·56)가 **전부 파이프가 아니었습니다** — 매번 폴백을 타서
    들어간 파이프로 되돌아왔고, 우회로가 아무것도 사지 못했습니다. 값을 고치고, 빌드 시
    **출구가 실제 파이프 top 인지 검사해 아니면 앞쪽 최근접 파이프로 스냅**하도록 했습니다
- **코스는 복원, 재생성 아님** — 되돌아올 때 레벨을 다시 만들면 이미 처리한 적이 되살아나고 체크포인트 페넌트가
  내려갑니다. 코스 객체 그대로 보관했다가 복귀합니다 (검증: 같은 객체 · 표식 유지)
- **방 안에서 죽으면 코스로 복귀** — `startLevel()` 이 룸 상태를 함께 정리합니다
- 방 레이아웃의 제약 두 가지:
  - **11·12행은 출구 파이프 말고는 비워 둡니다.** 첫 초안은 (18,10)에 ? 블록을 뒀는데, 출구 파이프 바로 위라
    충돌이 히어로를 블록 위로 밀어 올려 **출구에 설 수조차 없었습니다**
  - **높은 코인 열은 바닥에서 닿지 않습니다**(점프 75px vs 128px). 벽돌 선반이 올라가는 길 — 보상이 경로입니다
  - 보상 블록을 `entry.tx % 3` 으로 갈랐는데 실제 입구 3개(46·58·44)가 그 중 두 경우만 찍어서
    **? 블록이 코드에만 존재하고 게임에는 한 번도 안 나왔습니다**. 모든 방에 ? 하나, 한 레이아웃에는 버섯

## 움직이는 리프트 (레벨 어휘 확장)

지형·블록·파이프·구덩이만 있으면 모든 코스가 같은 방식으로 읽힙니다. **움직이는 발판**은 빠져 있던 한 가지를
넣습니다 — 배치가 아니라 **타이밍**이 실력이 되는 지형.

- **코스당 2기**: 긴 평지 위를 왕복하는 **셔틀(수평 6~7타일)**, 높은 코인 열까지 올라가는 **리프트(수직 5타일)**
- **지상 루트에서 일부러 비켜 놓았습니다** — 모든 코스는 여전히 "오른쪽만 누르는" 봇으로 완주됩니다(72/72).
  리프트가 주는 것은 지상에서 닿지 않는 코인 뭉치. 통과 보장을 유지하면서 숙련자에게 할 일을 줍니다
- 코사인 왕복이라 양 끝에서 감속하고, **스텝 카운터의 순수 함수**여서 두 발판이 절대 어긋나지 않고
  체크포인트 부활 후에도 코스가 기대하는 위치에 정확히 놓입니다 (검증: 137프레임 진행 후 리스폰 → 위치 동일)
- **위에서만 단단합니다**. 사방을 막으면 올라가는 리프트가 플레이어를 천장에 끼워 죽이고, 움직이는 끝면이
  벽으로 밀어 넣습니다 — 둘 다 플레이어가 읽을 수 없는 죽음입니다. 아래·옆은 통과
- **스윕 판정**: 최고 낙하 속도 5.5px/f 가 8px 데크를 관통하지 못하도록, 밟기 판정과 같이 "스텝 시작 시
  발이 데크 위에 있었는가"를 봅니다 (정지 데크에 10~260px 낙하 26종 전부 착지)
- **라이더는 양축으로 고정**됩니다. 하강은 중력에 맡겨도 될 것처럼 보였지만(데크 최대 0.64px/f vs 중력 0.38)
  실측하니 500프레임 중 **69프레임 접촉이 끊겼고**, 그때마다 코요테 타임과 점프를 잃습니다
- 물리가 렌더 보간 필드(`px/py`)를 참조하던 것을 발견해 **자기 이전 위치를 직접 보관**하도록 고쳤습니다 —
  보간 없이 시뮬레이션을 돌리는 순간 깨지는 구조였습니다 (실제로 테스트에서 깨졌습니다)

## QA 패스에서 잡은 결함

플레이어가 의존하는 규칙을 하나씩 실제로 실행해 보고, 상태·입력 경계를 뒤졌습니다. 발견한 것들:

- **점프·발사 입력이 상태를 넘어 새고 있었음** — `jumpBuf` 가 READY 카드·클리어 연출·일시정지 중에도 쌓여서
  조작권이 돌아오는 순간 히어로가 멋대로 튀어올랐고, **일시정지 화면에서 F 를 누르면 실제로 화염구가 발사**됐습니다.
  라이브 플레이 조건(`state==='play' && !paused && 살아있음`) 하나로 게이트
- **탭을 벗어나도 게임이 계속 돌고 있었음** — blur 된 창에는 keyup 이 오지 않으므로, 오른쪽을 누른 채
  다른 탭으로 가면 히어로는 계속 걷고 시계도 계속 갔습니다. blur/visibilitychange 에서 **키 상태를 모두 해제하고
  진행 중인 코스를 일시정지**합니다 (타이틀·클리어 화면은 건드리지 않음)
- **별 무적이 끝나는 프레임에 적 안에 있으면 즉사** — 별이 막아 주던 겹침을 다음 프레임이 그대로 판정했습니다.
  무적이 끝날 때 일반 피격 무적 30프레임으로 인계
- **워커 5기가 구덩이 위에 스폰** — `P(70)`(gap 69-70), `P(88)`(gap 86-88), `P(90..92)`(gap 90-92).
  깨어나자마자 떨어져 회수되므로 코스가 설계한 조우가 아예 일어나지 않고, 플레이어에게는 "적이 나타나서
  구멍에 빠지는" 장면으로 보였습니다
- **적 배치 패스 두 개가 서로를 덮고 있었음** — 가시 재배치가 워커 칸에 착지하고, 구덩이를 피한 워커가 다른 워커
  칸으로 이동했습니다(24코스에서 32건 중복). **순서 있는 단일 배치 패스**로 통합: 지면 필수 → 가시는 상공까지
  트인 칸 우선(없으면 지면으로 완화) → 한 칸에 한 마리
- **대형 폼이 여전히 다른 캐릭터로 보였음** — 컨택트 시트에서 실측한 결과 머리 비중이 소형 41% / 대형 31%,
  몸통은 5.7→12.3px(2.16배)인데 머리는 6.8→9.3px(1.37배)였습니다. 머리 반지름 4.7→5.3, 몸통 3.9→4.2,
  팔 6.2→7.6, 힙 21.0→21.7로 재조정 → **머리 비중 33%**. 프레임은 14→16px(히트박스 12px 유지,
  좌우 2px 오버행 — 18px 로 넓히면 벽에 붙었을 때 3px 파고듦), 스키드 포즈의 lean 은 대형에서 절반으로
  줄여 MOCHI 의 포니테일이 프레임 밖으로 잘리던 것 수정. **90개 히어로 스프라이트 전부 클리핑 0**

## 오디오·투사체·모바일 패스

- **백그라운드 복귀 시 음악이 폭발** — `setInterval` 스케줄러가 `nextTime` 이 밀린 만큼을 한 틱에 몰아서 예약합니다.
  30초 이탈 후 한 틱에 **197노트**(정상 2노트)가 동일 시점에 시작 = 클리핑 폭발. 0.5초 이상 밀리면
  프레이즈를 다시 시작하도록 클램프 (고정 타임스텝 루프의 `dt > 250` 가드와 같은 규율).
  0.2초 정도의 히컵은 그대로 따라잡습니다
- **화염구가 화면 밖에서 슬롯을 물고 있었음** — 벽/구덩이/좌측 이탈에서만 죽어서, 평지에서 오른쪽으로 쏘면
  화면 밖 118px까지 1.4초간 튀며 살아 있었습니다. 슬롯이 2개뿐이라 **쏠 수 없는 한 발**이 됩니다.
  원작처럼 화면 우측을 벗어나면 회수. 아이템은 일부러 제외 — 카메라를 앞질러 간 버섯은 아직 따라갈 수 있는 보상
- **적 배열만 압축되지 않고 있었음** — 아이템·화염구·파티클·팝업·범프는 매 프레임 in-place 압축하는데
  적은 `gone` 플래그만 세우고 배열에 남아, 코스 전체 인구(46)를 계속 순회했습니다(업데이트·드로우·쉘 충돌 3곳).
  같은 압축 적용 → 진행에 따라 46 → 32 → 8로 실제 감소
- **랜드스케이프 폰에서 플레이필드가 화면 높이의 60%** — 패드 자리를 위해 108px 밴드를 예약했는데,
  4:3 뷰는 넓은 화면에서 좌우가 어차피 비어 있어 패드는 캔버스 **옆**에 놓입니다. 예약 제거 →
  300x225 에서 **430x323(높이의 86%)**. 우측 3버튼(216px)이 여백(191px)보다 넓어 B가 코스 위에 겹치던 것은
  B·F 를 위로 감싸 146px 로 줄여 해결 (812x375 에서 5개 버튼 전부 캔버스와 겹치지 않음 검증)
- **포트레잇 폰의 죽은 공간** — 375x812 에서 플레이필드는 가로 제한으로 355x266, 656px 박스에 약 390px 이 남습니다.
  상단 고정은 그 여백을 게임 아래 하나의 공백으로 몰아 레이아웃이 깨진 것처럼 보였습니다.
  700px 이상 높이에서는 **하단 밴드에 파워업 설명**을 넣고(폰 플레이어는 키보드 안내를 볼 수 없음)
  플레이필드를 상단에 두어, 시선은 위 · 참고 정보는 엄지 바로 위 · 공백은 그 사이 한 곳으로 정리

## 게임 내용

- 타이틀: 캐릭터 선택(+해금된 시작 월드 선택) → **x-1 / x-2 / x-3 필드 코스 + x-4 요새** → 다음 월드
- 필드 레이아웃 **5종**(평지 3 + 테라스 1 + 수중 1)이 월드마다 밀리며 3개씩 선택됨
- 코스마다 전용 테마: **MEADOW**(낮) / **SUNSET**(석양) / **MIDNIGHT**(밤, 별 배경)
- 월드가 올라갈수록 적이 조금씩 빨라지고(최대 +45%), **시드 변주로 적·클러스터·리프트가 추가되며

  - **최고 낙하 속도(5.5px/f)에서의 밟기** — 한 스텝에 적의 어깨선을 지나쳐 버려, 분명히 머리 위로 떨어졌는데
    측면 접촉이 되던 구간이 있었음. 같은 이전 위치 판정으로 해결 (침투 0~8px는 항상 밟기, 빠른 낙하는 9px까지)

## 부드러운 조작감 (고도화) 구현

- **고정 60Hz 타임스텝** — 120/144Hz 디스플레이에서도 게임 속도가 동일 (rAF 직결 시 2배속으로 돌던 문제 해결)
- **렌더 보간(장면 전체)** — 시뮬레이션은 60Hz 고정(결정성 필수)이지만, 120Hz 화면에서 같은 스텝을 두 번
  보여주면 움직임이 계단처럼 보임. 남은 시간(`acc/STEP_MS`)으로 **카메라·플레이어·적·아이템·화염구·파티클·
  팝업 전부**를 보간. 카메라와 플레이어만 보간하면 나머지가 60Hz로 남아 매끄러운 카메라 대비 오히려 더 튐 —
  전부 보간하거나 전부 안 하거나 둘 중 하나여야 함 (alpha 0.5에서 모든 레이어가 정확히 반 스텝 이동 검증).
  스폰·리스폰·깃대 접촉·쉘 변환 같은 순간 이동은 스냅해서 보간이 번지지 않게 처리
- 카메라 하나로 통일 — 이전엔 타일이 `camQ()`, 스프라이트가 원본값을 써서 최대 0.5px 어긋날 수 있었음
- 정수배 백버퍼 + `image-rendering: pixelated` → 컨테이너를 꽉 채우면서 픽셀 유지
- 카메라 이징 (lerp, 뒤로 스크롤 없음)
- 코요테 타임 + 점프 버퍼 (점프 타이밍 관대)
- **속도 연동 점프** — 달리면 +11.5px 더 높이 (원작 방식). 보너스는 가산만 하므로 정지 점프 높이는 절대 낮아지지 않음
- 스퀴치 & 스트레치 점프/착지 애니메이션 (좌·우 동일 적용)
- 3프레임 걷기 사이클 + 브레이크(스키드) 프레임 + 브레이크 먼지, 이동 거리 기반 재생 속도

- 4레이어 패럴랙스 배경 (원경 능선 0.2 / 언덕 0.4 / 구름 0.6 / 수풀 1.0), 시드 고정
- **엇쌓기(running bond) 석조 타일** — 한 타일에 8px 2단, 세로 줄눈이 단마다 어긋나 이어 붙여도 격자로 보이지 않음
- **노출면만 캡 처리** — 위가 막힌 타일은 평면 내부 타일을 사용. 타일마다 베벨을 넣으면 큰 덩어리 내부에 밝은 수평선이 생겨 계단이 "쌓아올린 상자"로 보임
- **벽돌 ≠ 지면** — 부술 수 있는 벽돌은 세 테마 모두에서 지면보다 확실히 어둡고 채도가 높음 (이전엔 색차가 몇 % 수준)

## 화면 / 반응형

**표현은 반응형, 게임플레이는 고정.** 플레이필드는 어떤 화면에서도 **320x240 논리 해상도**입니다.

앞을 얼마나 볼 수 있는지는 레이아웃이 아니라 게임플레이 변수입니다. 창 크기에 따라 시야가
16칸↔26칸으로 달라지면 반응 시간과 구덩이·파이프를 읽는 방식이 바뀌고, 하이스코어도 창 크기가
다르면 비교할 수 없습니다. 이 파일의 지오메트리 검증(등반 높이, 구덩이 활주 거리)도 하나의
시야 기준으로 수행됐습니다. 그래서 게임 뷰포트는 고정이고, 남는 공간은 정직하게 레터박스입니다.

- 구조는 `header / 게임 박스(1fr) / footer` 그리드. 게임 박스가 `fit()` 이 실측하는 대상이고,
  그 안에서 4:3을 유지하며 최대 크기로 스케일됨
- **남는 공간은 게임이 아니라 크롬이 사용** — 가로 1100px 이상이면 조작 안내가 우측 **측면 열**로 이동해
  게임을 늘리지 않고 여백을 활용
- 프레임(`#stage`)이 플레이필드를 정확히 감싸므로 남는 공간은 페이지 배경으로 보임 ("빈 패널"이 아님)
- **상단바 우측 상태 표시** — HERO / BEST / SOUND·MUSIC. 넓은 레이아웃에서 팁을 숨기면 브랜드만 남고
  1000px 이상이 빈 공간이 됐음. 인게임 HUD에 없는 정보만 표시하고, 값이 바뀔 때만 DOM에 기록
  (매 프레임 쓰면 레이아웃 플러시가 발생)
- **인게임 HUD는 5등분 중앙 정렬** — 이전에는 좌측 여백에서 순차 배치해 우측에 72px이 남았음 (현재 좌 15 / 우 20)
- `fit()` 이 컨테이너의 **content box**를 실측 — `getBoundingClientRect()`는 padding을 포함한 border box라
  그대로 쓰면 캔버스가 축마다 20px 커지고 `overflow:hidden` 에 조용히 잘림 (높이 제한 시 지면 행이 날아감)
- 리사이즈 이벤트는 힌트로만 취급 — 레이아웃 확정 전에 알림이 오면 옛 크기로 계산되고 재시도 신호가 없음.
  루프가 매 프레임 컨테이너 client 크기를 비교해 **변했을 때만** 재계산 (0.0002ms, 프레임의 0.001%)
- 컬링 여유·타일 스팬(22열)·카메라 선행거리(109px)는 모두 논리 해상도에서 파생 — 한 곳만 바꾸면 됨
- 화면 높이 620px 미만이면 파워업 안내, 520px 미만이면 하단바 전체가 접힘. 가로 560px 미만이면 상단 팁 숨김
- 세로 모드 터치(높이 700px+)에서는 캔버스 상단 정렬 + 하단 밴드에 파워업 설명, 가로 모드에서는
  패드 예약 밴드를 없애 캔버스가 화면 높이의 86%를 사용 (패드는 캔버스 옆)

## 최적화

프레임 예산의 대부분은 픽셀 폰트가 쓰고 있었습니다. 텍스트가 lit 픽셀마다 `fillRect`를 호출하고
그림자까지 2패스라 HUD만으로 프레임당 `fillRect` 약 2800회였습니다.

| 항목 | 최초 | 현재 |
|---|---|---|
| HUD | 0.609ms | **0.077ms** |
| draw 전체 | 0.587ms | **0.321ms** |
| update | 0.022ms | **0.002ms** |
| 60Hz 프레임 예산 점유 | 3.7% | **1.9%** |

> 재측정(현재 빌드, 배치 측정 후 `getImageData`로 캔버스 큐 강제 flush):
> update 0.0013~0.0036ms / draw(play) 0.08~0.15ms →
> 프레임 **0.013~0.15ms = 60Hz 예산의 0.08~0.91%** (배치 크기·GPU 큐 상태에 따라 편차가 큽니다.
> 가장 나쁜 표본을 기준으로 봐도 예산의 1% 미만). 표의 값과 측정 방식이 달라 별도로 적어 둡니다
> (브라우저가 `performance.now()`를 coarsen 하므로 프레임 단위 측정은 0으로 나옵니다).

- **글리프 아틀라스** — 색상별 글리프 시트를 1회 렌더링, 문자당 `drawImage` 1회
- **문자열 캐시(FIFO 128)** — 정적 라벨은 문자열당 `drawImage` 1회
- **volatile 텍스트** — 점수·타이머처럼 매번 값이 바뀌는 문자열은 캐시를 건너뛰고 글리프 단위로 블릿. 캐싱하면 매초 새 캔버스를 만들어 플레이 중 히치가 생김
- **캐시 프리워밍** — 점수 팝업·라벨을 로드 시점에 미리 구움 (팝업은 하필 액션이 일어나는 순간 처음 등장함)
- **좌우 반전을 저장하지 않음** — NES가 OAM flip 비트로 PPU에서 미러링했던 방식대로 출력 시점에 음수 스케일로 반전. 반전 사본을 굽던 방식은 캔버스 180개 중 90개가 중복이었고, 그 대가로 얻는 건 프레임당 좌향 스프라이트 1개의 캔버스 상태 호출 3회뿐 (반전 결과는 사전구운 것과 90개 전부 픽셀 일치 검증)
- 하늘/HUD 그라디언트 캐싱, 배열 in-place 압축(프레임당 할당 5회 제거)
- **카메라 뒤 엔티티 회수** — 코스 진행에 따라 적 39 → 0

### 재점검 (이번 라운드)

핫패스(update/draw, 파티클·아이템·팝업 갱신, 카메라 컬링)를 다시 훑었지만 새로 짤 게 없었습니다 — 이전
라운드에 이미 처리된 것들(글리프 캐시, 배열 in-place 압축, 카메라 앞뒤 컬링)이 여전히 잘 버티고
있었습니다.

측정 중 요새 코스에서 **프레임당 83.8ms**(예산의 5배)로 읽히는 표본이 한 번 나왔습니다.
`update()`는 정상(0.003ms)이고 `draw()`만 65ms — 코드 결함처럼 보였지만, 같은 시나리오를 여러 번
독립적으로 재현해도 다시 나오지 않았습니다. 당시에는 `getImageData`가 캔버스를 소프트웨어 판독
모드로 전환시킨 부작용으로 추정하고, 근거 없이 "고쳤다"고 적지 않았습니다.

**(해결) 원인이 규명됐습니다.** 브라우저에서 시뮬레이션을 직접 스텝시킬 수 있게 된 뒤 다시 재보니
같은 현상이 **재현되고, 심지어 규칙적**이었습니다. 20코스 각 900프레임에서 `draw()` 평균은
0.105~0.569ms인데 최대값만 45~66ms로 튀고, 1-4를 세 번 재면 매번 정확히 3/900, 1-1은 매번 1/900.

계측기(`drawImage` 래퍼의 배열 할당)를 떼도 그대로였습니다. 결정적 단서는 **간격**이었습니다:

| 코스 | `draw` 평균 | 초당 draw | 예측 간격 (60Hz 컴포지트) | 관측 간격 |
|---|---|---|---|---|
| 요새 1-4 | 0.57ms | 1,754 | 약 29 draw | **25~26** |
| 필드 1-1 | 0.17ms | 5,882 | 약 98 draw | **93~100** |

간격이 draw 비용의 **역수로 정확히 스케일**합니다. 즉 스파이크는 게임의 히치가 아니라 **브라우저
컴포지터의 주기적 작업이, 마침 실행 중이던 `draw()` 호출에 청구된 것**입니다. rAF 밖에서 tight
loop로 재면 그 작업을 흡수할 프레임이 따로 없으니 한 표본에 몰립니다.

실제 rAF 프레임 페이싱 안에서(가장 무거운 요새, 6초, 735프레임 = 122.5fps) 재측정:

| | |
|---|---|
| `draw` | 평균 0.245ms · p95 0.3 · **p99.9 0.6 · 최대 0.6ms** |
| `update` | 평균 0.031ms (367회 호출 = rAF 2회당 1스텝) |
| 프레임 JS 비용 | 평균 0.261ms · 최대 0.6ms · **8.3ms 초과 0회 · 16.67ms 초과 0회** |
| 프레임 간격 | 평균 8.33ms · 최대 11.0ms · **16.67ms 초과 0회 = 드롭 프레임 0** |

45~66ms 스파이크가 **완전히 사라집니다.** 최악 프레임의 JS 비용은 0.6ms로 60Hz 예산의 1/28,
120Hz 예산의 1/14입니다. 83.8ms도 같은 계열의 측정 아티팩트였다고 이제 근거를 갖고 말할 수 있습니다 —
`getImageData` 가설이 아니라 **rAF 밖 측정**이 원인입니다.

한 가지는 명시해 둡니다: 이 숫자는 **JS 명령 제출 비용**입니다. 래스터·컴포지트는 다른 스레드에서
일어나고 `draw()` 주변의 벽시계로는 볼 수 없습니다. 강제 플러시에는 예전 측정을 오염시킨 바로 그
호출(`getImageData`)이 필요하므로 쓰지 않았습니다.

대신 환경 잡음에 안 흔들리는 지표(프레임당 `drawImage` 호출 수)로 다시 확인:

| 코스 | 드로우 콜 |
|---|---|
| 필드 | 118 |
| 라군 | 168 |
| 요새 | 473 |
| 테라스 | 113 |
| 보너스 룸 VAULT | 202 |
| 보너스 룸 CHIMNEY | 322 |
| 보너스 룸 TUNNEL | 312 |
| 타이틀 | 64 |

기존 실측(필드 122 / 라군 170 / 요새 464 / 테라스 122)과 오차범위 내로 일치하고, 이번 세션에 새로 생긴

> **정직하게 남기는 단서** (2026-08-20 gstack QA): 아래 표 전반에 쓰인 "통과 주행" 판정 조건

> 죽고 리스폰한 주행이 "클리어"로 잘못 집계될 수 있었습니다. 즉 **아래 표의 "N주행 전부
> 클리어" 문구들은 죽고도 클리어로 보이는 주행을 걸러내지 못하는 조건으로 측정된 것**입니다.

>
> **그리고 이 조사에서 "통과 주행"이라는 지표 자체의 한계도 드러났습니다.** 최초 재검사에서
> MOCHI·BOLT가 16개 조합에서 실패했는데, 적응형 봇으로 바꾸자 BOLT는 8개 전부 통과 —
> 즉 상당 부분이 **봇 정책의 한계**였습니다. 반대로 봇을 "개선"했더니 통과했던 BOLT가
> 퇴행하기도 했습니다. 통과/실패 이진 지표는 봇 정책에 너무 민감해서 레벨 품질의 대리
> 지표로 쓰기에 약합니다. 그래서 이번 라운드부터는 **봇 정책과 무관한 지표**를 씁니다:
> 전속 주행 상태에서 이륙 타이밍을 립-0부터 립-5까지 훑어 **몇 개가 성공하는가(관용 창)**.

### ISSUE-003 — 구덩이 공중 정리 창이 이륙 지점을 못 덮고 있었습니다 (수정 완료)

"구덩이 위 공중은 비운다" 규칙이 `{구덩이-1 … 구덩이+1}`만 정리했습니다. 이륙이 립에서
일어난다는 가정인데, **전속 주행 시 히어로는 립보다 2~3칸 앞에서 발이 떠고**, 그 뒤로도
약 2.8칸을 상승하며 머리가 그 행들을 지나갑니다 (실측 상승 스윕: BOLT 1.90 / PIP 2.19 /
MOCHI 2.83 타일, 주행 속도 2.54 / 2.70 / 3.02 px/프레임).

레이아웃 2가 정확히 그 형태였습니다 — 9행 86~88열에 `?` 그룹, 90~92열에 3타일 구덩이.
창이 89~93열만 비워서 **88열 블록이 이륙 지점에 그대로** 남았습니다. MOCHI(점프 최저·속도
최고 = 가장 일찍 떠고 여유 높이가 가장 적음)가 상승 중 그 블록에 머리를 박아 `vy`가 한
프레임에 **-6.81 → 0.5**로 죽고, 구덩이 반대편 벽에 붙은 채 떨어졌습니다. 월드 1-3, 2-2,
3-1, 6-3, 7-2, 8-1, 11-3, 12-2 그리고 이후 매 5번째 코스마다 재현됩니다.

접근 측 창을 **1칸 → 3칸**으로 넓혔습니다. 보상 블록은 삭제가 아니라 좌측 이전이므로
콘텐츠 손실은 없습니다(보상 697개·코인 2779개 보존 확인).

측정(봇 정책과 무관한 관용 창 지표):

| | 해당 구덩이 (3히어로 전부) | 전체 138개 구덩이×히어로 쌍 평균 |
|---|---|---|
| 수정 전 | **2/6** 이륙 타이밍만 성공 | 4.20/6 |
| 수정 후 | **4/6** | **4.96/6** |

회귀: 48코스 구조 무결성(구덩이·용암 공중, 워커 접지, 수중 통행) 유지, 렌더 180장 예외 0,
몽키 소크 40k 스텝 예외 0·NaN 0.

### ISSUE-004 — 가시의 "열린 하늘"도 같은 곳을 잘못 보고 있었습니다 (수정 완료)

ISSUE-003을 고친 뒤 **같은 버그 클래스가 인접 규칙에도 있는지** 찾아봤고, 있었습니다.
`airClear()`는 `{가시-2 … 가시+2}`의 공중이 비었는지만 봤습니다. 그런데 SPIKO는 밟을 수
없어서 답이 점프뿐이고, 그 이륙은 가시보다 2~3칸 앞에서 일어나 그 뒤로도 약 2.8칸 상승합니다.
즉 **가시 뒤 3~5칸의 블록이 정작 그 점프를 잘라먹고** 있었습니다. 해당 블록의 주석은 처음부터
이 실패를 정확히 서술하고 있었습니다("`?` 그룹 앞에서 이륙한 모든 접근이 머리를 박고 가시
위로 떨어졌다") — 검사 대상 열만 틀렸던 것입니다.

24코스에서 접근 폭을 스윕해 측정:

| 접근 창 | 남은 가시 | 접근부가 막힌 가시 | 평균 관용 창 |
|---|---|---|---|
| 2 (기존) | 94 | **66** | 2.97/6 |
| 3 | 96 | 65 | — |
| 4 | 77 | 39 | — |
| **5 (채택)** | 64 | **0** | **4.21/6** |

5를 골랐습니다 — 막힌 가시를 0으로 만들고 평균 관용 창을 2.97 → 4.21/6으로 올립니다
(≤1/6이던 39쌍이 전부 사라짐). 대가는 자리가 안 나 **일반 워커로 퇴화하는 가시 30개**인데,
이건 이 파일이 이미 명시적으로 택한 트레이드오프입니다 — "불공정한 적보다 좁은 자리의
공정한 적이 낫다".

측정 과정에서 제 하네스 버그도 하나 더 잡았습니다: **SPIKO는 걸어서 다가오는데** 처음엔
빌드 시점의 고정 열로 이륙 타이밍을 계산해서 전 구간 0/6이 나왔습니다 — 가시의 **실시간
위치** 기준으로 고쳐야 의미 있는 수치가 나옵니다.

회귀: 48코스 clean(가시 108개 전부 접근부·하늘 개방, 구덩이·용암 공중, 워커 접지, 수중 통행),
보상 693개·코인 2775개, 렌더 180장 예외 0, 몽키 소크 50k 스텝 예외 0·NaN 0.

### 하네스: 브라우저에서 실제 엔진을 직접 스텝시키기

여태 계측은 두 갈래였고 둘 다 한쪽 눈을 감고 있었습니다. Node 하네스는 엔진 코드를 흉내내야
했고, 브라우저 하네스는 `requestAnimationFrame`에 묶여 있었습니다. 후자의 대가는 실측으로
드러났습니다 — **헤드리스 rAF는 121Hz**이고 엔진은 고정 60Hz 누산기이므로 rAF 2회당 시뮬레이션
1스텝입니다. rAF로 입력 유지 시간을 세면 **의도한 절반 길이의 입력**이 들어갑니다.

`update()`가 단일 스텝 함수라는 점을 이용하면 양쪽 문제가 같이 사라집니다:

```js
window.requestAnimationFrame = () => 0;   // 게임의 루프는 스스로 재등록하므로 체인이 끊긴다
const _update = eval('update'), _draw = eval('draw');   // 최상위 const/let은 window에 없다
// 이제 스텝을 내가 소유한다 — 스텝 수가 결정적이고, 실시간의 약 120배로 돌아간다
```

이렇게 하면 **실제 게임 코드**를 20,000스텝 2.8초에 돌립니다(초당 약 7,100스텝). 코스 20개
50,000스텝이 15초입니다.

입력을 넣을 때 주의할 점이 하나 있습니다. `keys.jump = true`만으로는 **점프가 일어나지
않습니다** — `jumpBuf`는 keydown 핸들러에서만 세팅되고(`engine.js:3220`) 점프 개시 조건은
`jumpBuf > 0`입니다. `keys.jump`는 점프 **높이**만 조절합니다. 즉 점프는 상태가 아니라
**엣지**이고, 하네스도 그 엣지를 재현해야 합니다(`m.jumpBuf = 8`).

이 하네스로 잡는 것은 봇 실력과 무관한 것들입니다 — 던져진 예외, `NaN` 위치, 죽지 않고 레벨
아래로 떨어짐, 음수 카운터, 배열 무한 증가, 진행하지 않는 상태. **봇의 사망 지점은 여전히 레벨
품질의 증거가 아닙니다.** 실제로 이번에도 봇이 1-1의 tx 20에서 규칙적으로 멈춰 함정처럼
보였지만, 그 구간(12~34열)은 13~14행이 전부 지면인 완전 평지였고 원인은 제 점프 유지 로직이었습니다.
그리고 관용 창을 재구현할 때 립 9칸 전에 배치했다가 **4칸 파이프 앞**에 놓여 3히어로 전부
"함정"으로 집계된 것도 같은 함정을 다시 밟은 것입니다(README에 이미 기록돼 있던 실수).
지금 지표는 이륙 지점에 전속으로 직접 배치해서 수평 접근 장애물을 지표에서 배제하고,
상승 궤적(ISSUE-003/004가 다룬 머리 위 블록)은 그대로 검사합니다.

### ISSUE-005 — BOLT는 마른 땅에서 걸을 수 없었습니다 (수정 완료)

이번 라운드에 브라우저에서 **실제 엔진을 직접 스텝**시킬 수 있게 되면서(아래 하네스 절) 처음
드러난 결함이고, 이 프로젝트에서 지금까지 나온 것 중 가장 심각합니다.

`updateMario()`에는 마찰 잔여분을 죽이는 한 줄이 있었습니다:

```js
m.vx = Math.max(-maxV, Math.min(maxV, m.vx));
if (Math.abs(m.vx) < 0.05 && m.onGround) m.vx = 0;   // 무조건 실행
```

의도는 "키를 놓으면 미끄러지지 말고 멈춰라"였습니다. 그런데 **방향키를 누르고 있는 스텝에도
그대로 적용**됩니다. 그러면 매 스텝 가속을 더한 직후 0으로 되돌려지고, `vx`는 영원히
누적되지 못합니다. 그리고 그 임계값 0.05는 하필 **실제 가속값들의 정확히 한가운데**에 있습니다:

| | 가속 = 계수 × `ch.speed` | 0.05 대비 | 결과 |
|---|---|---|---|
| PIP 지상 걷기 | 0.05 × 1.00 = **0.0500** | 같음 | 살았음 (`0.05 < 0.05`가 false라서) |
| MOCHI 지상 걷기 | 0.05 × 1.12 = 0.0560 | 초과 | 정상 |
| **BOLT 지상 걷기** | 0.05 × 0.94 = **0.0470** | 미달 | **완전 정지** |
| PIP 수중 | 0.045 × 1.00 = **0.0450** | 미달 | **완전 정지** |
| MOCHI 수중 | 0.045 × 1.12 = **0.0504** | 초과 | 정상 |
| **BOLT 수중** | 0.045 × 0.94 = **0.0423** | 미달 | **완전 정지** |

즉 BOLT를 고른 플레이어가 달리기 키 없이 방향키만 누르면 **1-1 첫걸음부터 히어로가 전혀
움직이지 않습니다.** 수중에서는 PIP과 BOLT가 바닥에 닿는 순간 걸을 수 없게 되고(영법으로
바닥을 떠야만 전진 가능), MOCHI만 소수점 넷째 자리 차이로 멀쩡합니다. PIP의 지상 걷기가
살아있던 것도 설계가 아니라 **경계에 걸친 우연**입니다.

수정은 "이 스텝에 실제로 가속을 넣었는가"를 기록해서, 넣었으면 지우지 않는 것입니다:

```js
let steering = true;
if (keys.left && !keys.right) { m.vx -= acc; m.facing = -1; }
else if (keys.right && !keys.left) { m.vx += acc; m.facing = 1; }
else { steering = false; /* 마찰·항력은 여기서만 */ }
m.vx = Math.max(-maxV, Math.min(maxV, m.vx));
if (!steering && Math.abs(m.vx) < 0.05 && m.onGround) m.vx = 0;
```

측정 (적을 제거해 이동만 분리, 240스텝):

| | 지상 걷기 | 수중 | 지상 달리기 (회귀 확인) |
|---|---|---|---|
| PIP 전 → 후 | 317.1px → 317.1px | **0.0px → 164.0px** | 2.700 → 2.700 |
| MOCHI 전 → 후 | 355.2px → 355.2px | 164.0px → 164.0px | 3.024 → 3.024 |
| BOLT 전 → 후 | **0.0px → 298.1px** | **0.0px → 164.0px** | 2.538 → 2.538 |

최고 속도는 전부 문서값과 정확히 일치하고(걷기 1.4×, 달리기 2.7×, 수중 1.55× `ch.speed`),
데드존의 **원래 목적도 그대로**입니다 — 키를 놓으면 16~20px만 미끄러지고 45~48스텝에
`vx`가 정확히 0이 됩니다.

**이 버그가 여태 살아남은 이유**는 기록해 둘 만합니다. 이 프로젝트의 모든 봇이 **항상 달리기
키를 쥐고 있었습니다.** 달리기 가속은 0.07 × `ch.speed`(최저 0.0658)로 임계값을 늘 넘으므로,
어떤 봇도 이 코드를 밟을 수 없었습니다. 새 플레이어가 가장 먼저 쓰는 입력 — 방향키 하나 —
이 한 번도 테스트 대상이 아니었던 것입니다. 통과율이 높은 테스트가 아니라 **테스트가 건드리지
않는 입력**이 위험합니다.

회귀 검증 (수정 전/후 엔진을 각각 서빙해 동일 코드로 A/B):

- 관용 창 지표: 12코스·36구덩이·**108쌍 4.750/6·함정 0** — 수정 전과 **소수점 세 자리까지 동일**.
  (이 수정은 `|vx| < 0.05`에만 손대고, 이 지표는 전속 상태에서 시작하므로 원리상 무관합니다.
  추론에 맡기지 않고 측정으로 확인했습니다.)
- 20코스 소크 50,000스텝: 예외 0, 불변식 위반 0, 누수 0. 필드·요새 도달 거리는 수정 전과
  전부 동일하고, **수중 코스만 `maxTx` 3 → 25로 살아났습니다**.

같은 클래스 점검: `|vx| > 2`(먼지)와 `> 0.1`(걷기 애니메이션)은 모든 히어로가 의도대로
갈립니다. `speedBonus`의 `/ 2.7`이 `ch.speed`로 정규화돼 있지 않은 것은 발견했지만 결함으로
보지 않았습니다 — "절대 속도가 점프 높이를 사준다"는 읽기에서 일관되고, 가장 느린 BOLT는
`ch.jump 1.05`로 이미 설계상 보상받습니다. 이득 없이 물리를 흔들면 지오메트리 여유 전체를
다시 검증해야 합니다.

### 입력 퍼즈 — "테스트가 건드리지 않는 입력"을 겨냥해서

ISSUE-005의 교훈이 "봇이 늘 달리기 키를 쥐고 있어서 걷기가 한 번도 테스트되지 않았다"였으므로,
그 다음 라운드는 **여태 어떤 봇도 누르지 않은 입력**을 겨냥했습니다: 왼쪽, 아래(파이프),
F(화염구), 그리고 시스템 키 P/M/B/Q/Enter/Escape.

입력은 `keys` 객체를 찔러 넣는 대신 **실제 KeyboardEvent를 디스패치**합니다. `jumpBuf`,
일시정지, 음소거, 종료, 리바인드 화면이 전부 keydown 핸들러 안에 살기 때문에, `keys`만 찔러서는
그 경로를 통째로 건너뜁니다 — 걷기 버그를 숨긴 바로 그 사각지대입니다.

**처음 두 번의 퍼즈는 "이상 없음"을 냈고 둘 다 무효였습니다.** 커버리지 카운터를 붙여 보니
첫 번째는 80,000스텝 중 **71,199스텝(89%)이 일시정지 상태**였고, 두 번째는 **100%**였습니다.

보냅니다. 두 번째는 앞선 퍼즈가 정지 상태로 끝났는데 `startLevel()`이 `paused`를 초기화하지
않아 전체가 얼어붙은 것입니다. **통과 여부만 보면 둘 다 초록불이었습니다.**

### 일시정지 하드닝 — 도달 불가였지만 잠금이었던 조합

퍼즈를 고치는 과정에서 조합 하나가 드러났습니다. 일시정지 토글은 `state === 'play'`에서만
동작하고(`onKeyPress`), `update()`는 정지 중 **상태 전이를 전혀 하지 않습니다**. 따라서 정지
상태에서 `ready`가 되면 ready 타이머가 흐르지 않아 영원히 `ready`이고, 해제 키도 거부됩니다 —
**키보드로 빠져나올 수 없는 잠금**입니다.

**현재 플레이어는 이 상태에 도달할 수 없습니다.** 확인한 근거를 남겨 둡니다: 토글·종료·
`autoPause()`가 모두 `state === 'play'` 게이트를 가지고, 종료는 `paused`를 명시적으로 해제하며,
정지 중에는 `update()`가 상태를 바꾸지 않으므로 `paused ⟹ state === 'play'`가 성립합니다.
`paused`는 `saveSettings()`에 저장되지도 않으므로(`charIdx`/`muted`/`bgmOn`/`keys`만) 리로드
잠금도 없습니다. 이 조건을 만든 것은 정지 중에 `startLevel()`을 호출한 **제 하네스**였습니다.

그래도 잠재 위험은 실재합니다 — 나중에 "코스 재시작"이나 정지 메뉴 항목이 추가되면 곧바로
실제 잠금이 됩니다. 그래서 원인과 탈출구를 각각 한 줄로 막았습니다: `startLevel()`이 항상
`paused`를 해제하고(새 코스는 절대 정지로 시작하지 않는다), **해제**는 어떤 상태에서든 허용합니다
(정지는 여전히 `play`에서만 가능). 불변식을 "현재 경로들의 성질"에서 **구조적 보장**으로
바꾼 것입니다.

검증: 정지 중 `startLevel()` → 해제됨, `ready`에서 강제 정지 후 `p` → 탈출 가능, ready 타이머
재개 확인. 이것은 **버그 수정이 아니라 하드닝**입니다 — 출하 동작에서 발견된 결함이 아닙니다.

### 반응형 레이아웃 스윕 — 과거에 실제로 버그가 났던 자리

이전 라운드에 여기서 진짜 결함이 세 개 나왔습니다(세로 A버튼 41px 화면 밖 잘림, 파워업 문구 겹침,
랜드스케이프 9px 캔버스 침범). 그래서 눈으로 보는 대신 **뷰포트 행렬 × 두 입력 모드**로 못박았습니다.
터치 레이아웃은 미디어 쿼리가 아니라 `body.touch` 클래스로 갈리므로, `setupTouch()`가 하는 것과
동일하게 클래스와 `pad.hidden`을 세팅해 재현합니다.

검사 항목 — 보편 규칙: 수평 스크롤 0, 캔버스가 뷰포트 안에 완전히 들어오고 100px 이상, 터치 버튼
전부 24px 이상이며 화면 밖으로 나가지 않고 **캔버스를 침범하지 않음**, 파워업 문구가 패드 아래에
깔리지 않음.

그리고 **문서화된 단계적 접힘을 의도로서 양방향 검증**합니다: `max-height: 460px`에서 `#botbar`가
접혀야 하고(그보다 크면 반드시 보여야 함), `max-height: 540px`에서 `.sysbar`가 접혀야 하고,

## 페이지 크롬 — 아케이드 캐비닛

캔버스를 둘러싼 페이지가 개발자 테스트 페이지처럼 보였습니다. 차가운 남색 패널(`#0d1020`)이

"키 — 설명" 행이 쌓인 디버그 readout이었습니다. 헤더가 작은 산세리프로 "PIPO JUMP"를 말하는데
바로 아래 게임이 4배 픽셀로 같은 말을 하고 있었던 것도 히어로를 깎아먹었습니다.

방향은 **실제 캐비닛**입니다 — "레트로 테마 웹페이지"(픽셀 폰트 + 그림자)가 아니라 재질과

- **재질과 구조만** — 나무 텍스처·스캔라인·베벨 없음

- **캐비닛은 움직이지 않음** — 페이지의 모든 모션은 게임이 공급

### 서드파티 의존성을 0으로 되돌림

첫 디자인 라운드에서 제가 Google Fonts를 `<head>`의 **렌더 블로킹 스타일시트**로 넣었습니다 —
그전까지 네트워크 의존성이 0이던 게임에 서드파티 요청을 앞세운 것이고, **설치형 앱이 자기 라벨을
그리려고 네트워크를 필요로 하는 건 깨진 약속**입니다. `latin` 서브셋만 셀프호스팅으로 바꿨습니다
(400 3.5KB + 700 3.2KB = 6.7KB). 크롬이 렌더하는 문자는 A-Z·0-9·중점뿐이고, 화살표는
`keyName`이 'LEFT'/'DOWN' 텍스트로 바꾸므로 확장 서브셋이 필요 없습니다.

결과: **서드파티 요청 0, 총 요청 4개**(css, js, woff2 ×2). 네트워크 없이 렌더되고 플레이됩니다.
SIL OFL 1.1이라 `fonts/OFL.txt`를 함께 배포합니다(라이선스 요구사항).

### 오프라인 실행 — 캐시 무효화 함정을 피하는 선택

manifest로 홈 화면 설치는 되지만, 서비스 워커가 없으면 설치된 앱도 자기 HTML·CSS·엔진·폰트를
받으려고 네트워크가 필요합니다. 지하철에서 열면 빈 화면 — **온라인에서만 되는 설치형 앱**은
서드파티 폰트와 똑같은 종류의 깨진 약속입니다.

전략은 **cache-first가 아니라 network-first + 빠른 캐시 폴백**입니다. 이유가 핵심입니다:

이 프로젝트는 빌드 단계가 없어서 파일명에 콘텐츠 해시를 넣을 수 없습니다. cache-first로 가면
배포마다 버전 상수를 **손으로** 올려야 하고, 잊었을 때의 실패 모드가 최악입니다 — 플레이어가
옛 빌드에 고정되고, 본인은 알 방법이 없고, 서버에서 되돌릴 방법도 없습니다. network-first는
그 함정을 아예 없앱니다: 온라인이면 항상 배포된 것이 나오고, 캐시는 순수하게 "네트워크가 없을 때
게임이 돌아가게" 하는 용도로만 존재합니다.

대가는 온라인에서의 왕복 한 번인데, 이 페이지는 이미 그걸 내고 있었습니다(파일 4개, 서로
블로킹하지 않음). 죽은 네트워크에서 수십 초 매달리는 문제는 fetch를 **2.5초 타이머와 경쟁**시켜
처리합니다 — 30초 걸려 열리는 게임은 안 열리는 게임과 실질적으로 같습니다.

세부 결정 둘:
- 프리캐시는 `cache.addAll`이 아니라 **개별 요청**으로 합니다. `addAll`은 하나라도 404면 install
  전체를 거부해서, 아이콘 하나 이름이 바뀌었다고 오프라인 지원이 통째로 사라집니다
- `res.ok && res.type === 'basic'`만 캐시합니다. 오류나 opaque 응답을 캐시하면 정작 보호하려던
  오프라인 경로가 오염됩니다

**로직 검증**: `sw.js`를 모의 워커 스코프에 로드해 **실제 핸들러를 실제 CacheStorage로**
구동해 12항목을 통과시켰습니다: 프리캐시(404 하나 포함), skipWaiting, 구버전 캐시 삭제,
clients.claim, 온라인 network-first, 오프라인 캐시 서빙, 느린 네트워크의 2.5초 타임아웃 폴백,
오프라인 내비게이션의 셸 폴백, non-GET·크로스오리진 통과, 캐시 없는 미스의 에러 응답.

**브라우저 end-to-end 검증 (완료)**: 오래 미검증으로 남아 있던 항목입니다. 이전 자동화 브라우저는
서비스 워커 등록 자체를 차단했지만(스크립트는 200 + 올바른 MIME인데 등록 전용 내부 fetch만 실패),
실제 Chromium + `127.0.0.1`(secure context)에서 마침내 확인했습니다. 순서가 중요합니다 —
**서버를 죽인 뒤**에 측정해야 캐시가 실제로 일하는지 알 수 있습니다:

| 단계 | 측정값 |
|---|---|
| 등록 | scope `/`, state `activated` |
| 프리캐시 | SHELL 12/12, 누락 0, 캐시 이름 `pipo-v1` 하나뿐 |
| 서버 종료 | `curl` exit 7 (connection refused) — 페이지 관점의 fetch도 reject |
| 재방문 | 서버 죽은 상태로 `index.html` 로드 성공, 반복 내비게이션도 성공 |
| CSS | 52 rule, `#stage` border-radius `6px` — 알몸 HTML이 아니라 캐비닛 그대로 |
| 폰트 | `document.fonts.check('16px Silkscreen')` = true (자체 호스팅 woff2가 캐시에서) |
| 엔진 | `GAME`·`TILE`·`KEYS_MAP` 살아있음, 레벨 빌드됨(flagX 198, 제한시간 400) |
| 플레이 | 달리기 vx **2.70** = 문서화된 PIP 속도와 일치, tx 3 → 38, 코인 3, 점수 600, 타이머 400 → 345 |
| 렌더 | 캔버스 발광 샘플 12,129 / 167색 |
| 콘솔 | 실제 에러 0 (뜬 1건은 네트워크 사망을 확인하려 **내가 일부러 던진** probe fetch) |

즉 오프라인에서 페이지가 뜨는 수준이 아니라 **물리·득점·타이머·사망/리스폰까지 도는 게임**입니다.

여기서도 하네스 버그를 두 개 잡았고, 둘 다 제 쪽입니다. (1) `'GAME' in window`가 false여서 엔진이
안 돌았다고 잘못 읽었습니다 — 최상위 `const`/`let`은 window에 얹히지 않고 전역 렉시컬 스코프에
있습니다. (2) 헤드리스 rAF가 **121Hz**라서, 엔진의 고정 60Hz 누산기 기준으로 rAF 2회당 1스텝입니다.
점프 유지를 rAF로 세던 봇은 실제로 **절반 길이 점프**를 하고 있었습니다. 봇이 tx 20에서 멈춘 것을
지형 함정으로 오해할 수 있었지만, 그 구간 지도를 뜯어보니 12–34열은 13–14행이 전부 지면인 완전 평지였습니다.
**봇 성적을 레벨 품질의 증거로 쓰지 않는다**는 이 프로젝트의 원칙이 또 맞았습니다.

**배포 측 짝 — `_headers`**: 워커 전략이 맞아도 전달이 틀리면 소용없습니다. `sw.js`가 캐시에
붙들리면 **network-first 워커조차 옛 동작에 사람을 고정시킬 수 있습니다** — 페이지는 이미 가진
워커를 계속 돌리고 교체본을 영영 안 봅니다. 브라우저가 자체적으로 워커 스크립트 캐시를 24시간으로
제한하지만, 24시간은 고친 게 이미 배포됐는데 버그가 살아있는 하루입니다. 그래서:

| 경로 | 정책 | 이유 |
|---|---|---|
| `/sw.js` | `no-cache` | 교체본이 즉시 내려가야 함 |
| `/`, `/index.html`, manifest | `no-cache` | 앱이 **무엇인지**를 정의(자산 이름·시작 URL) |
| `/css/*`, `/js/*` | `max-age=0, must-revalidate` | 콘텐츠 해시가 없으니 immutable로 둘 수 없음 — 긴 max-age는 새 HTML에 옛 코드를 붙임 |
| `/fonts/*` | `max-age=1년, immutable` | 이름이 고정이고 바이트가 안 바뀜. 교체가 필요하면 이름을 바꿈 |
| `/*.png` | `max-age=1주` | 같은 이유, 조금 짧게 |

`cache.put`의 rejection도 막았습니다. 응답은 페이지로 즉시 보내야 하므로 `put`을 await하지
않는데, 그러면 rejection이 **unhandled로 새어나갑니다**. `put`은 정당하게 실패할 수 있고
(용량 초과 등) 실패해도 잃는 건 최적화뿐입니다. 검증 중 이 테스트가 처음엔 통과처럼 보였는데
`putAttempts=0`이었습니다 — 제가 만든 모의 `Response`는 `type: 'default'`라 `'basic'`만 캐시하는
분기를 아예 안 탔던 것입니다. 실제 same-origin fetch로 바꿔 5항목 전부 통과 확인.
